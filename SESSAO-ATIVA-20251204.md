● 🔐 Arquitetura de Segurança e Privacidade - TalkerApp

  Dado o contexto (dados sensíveis = pensamentos, emoções, comportamentos inconscientes), vou propor
 uma arquitetura em camadas de segurança:

  ---
  1. CAMADA DE ARMAZENAMENTO

  1.1 Dados em Repouso (Database)

  Problema: SQLite local contém transcrições + análises sensíveis

  Soluções Propostas:

  Opção A: Criptografia de Database (Simples)

  - Ferramenta: SQLCipher (SQLite with encryption)
  - Como funciona: Database inteira criptografada com AES-256
  - Chave: Derivada de senha do usuário (PBKDF2 ou Argon2)
  - Prós:
    - Simples de implementar
    - Database inacessível sem senha correta
    - Performance boa (criptografia em nível de página)
  - Contras:
    - Se usuário perder senha, perde tudo
    - Chave fica em memória enquanto app está aberto

  Opção B: Criptografia por Campo (Granular)

  - Como funciona: Apenas campos sensíveis criptografados (transcription, analysis_text)
  - Ferramenta: Node.js crypto module (AES-256-GCM)
  - Chave: Mesma estratégia (derivada de senha)
  - Prós:
    - Metadata não criptografada (permite busca por data, duration, etc)
    - Mais flexível
  - Contras:
    - Mais trabalhoso implementar
    - Risco de vazar dados se implementação estiver errada

  Opção C: Criptografia Zero-Knowledge (Avançado)

  - Como funciona: Chave de criptografia NUNCA sai do dispositivo do usuário
  - Implementação:
    - Gerar par de chaves assimétricas (RSA ou Curve25519)
    - Chave privada fica no device (localStorage com crypto)
    - Chave pública no servidor (se houver sync)
  - Prós:
    - Máxima segurança (nem você, desenvolvedor, acessa os dados)
    - Modelo "privacy-first" de verdade
  - Contras:
    - Complexo
    - Se usuário perder device + backup, dados irrecuperáveis

  Minha Recomendação: Opção A (SQLCipher) para começar
  - Equilíbrio segurança/complexidade
  - Usuário define senha ao primeiro uso
  - Backup da chave em arquivo separado (opcional)

  1.2 Áudio Gravado

  Problema: Blob de áudio fica em IndexedDB antes de processar

  Soluções:

  Estratégia Proposta:

  1. Áudio gravado → IndexedDB (temporário)
  2. Após transcrição bem-sucedida:
    - Opção A: Deletar áudio imediatamente
    - Opção B: Criptografar e manter (caso usuário queira reouvir)
  3. Se transcrição falhar:
    - Manter áudio criptografado localmente
    - Retry automático quando servidor voltar

  2. CAMADA DE TRANSPORTE

  2.1 Comunicação com APIs Externas

  Fluxo atual:
  Browser → Next.js API Route → Whisper API → Claude API

  Riscos:
  - Dados trafegam pela internet (Whisper + Claude são serviços externos)
  - Man-in-the-middle attacks
  - Logs de APIs externas

  Soluções:

  2.1.1 HTTPS Obrigatório

  - ✅ Já deve estar implementado
  - Certificar que localhost também usa HTTPS em produção

  2.1.2 Não Logar Dados Sensíveis

  // ❌ NUNCA fazer:
  console.log("Transcription:", transcription);
  logger.info({ transcription }); // Logs podem vazar

  // ✅ Fazer:
  console.log("Transcription length:", transcription.length);
  logger.info({ transcriptionId, duration, timestamp }); // Só metadata

  2.1.3 Política de Dados das APIs

  Whisper (OpenAI):
  - Por padrão, OpenAI NÃO treina em dados enviados via API (desde Mar/2023)
  - Mas dados transitam pelos servidores deles
  - Solução: Aceitar o risco OU migrar para Whisper local (mais complexo)

  Claude (Anthropic):
  - Mesma política: não treina em dados de API
  - Solução: Idem acima

  - Adicionar aviso claro ao usuário: "Seus áudios são transcritos por Whisper (OpenAI) e analisados
